## S15a. Режим тестирования баланса

**Состояние:** реализовано. Сценарий — данные (`shared/config/sandbox.ts`),
проверка и расстановка — `features/sandbox`, старт — `initializeSandbox`,
UI — `widgets/game-controls/ui/sandbox`, headless — `scripts/sandbox-balance.test.ts`.
Урон считается полученным по типам цели (кто нанёс — не различается);
ручная правка расстановки кликом не сделана — есть команды отладки S02a.
Проверено: unit (сценарий, расстановка), интеграционно (старт, пустое поле,
отказ, итоги, пассивная сторона, сброс), браузер — бой ИИ против ИИ на 15×15
до конца с итогом, без ошибок консоли.

Зависимости: S02a, S14b. Выполнить сразу после S15: баланс проверяется в
S16, S17, S17a и S21, и каждый раз нужна быстрая постановка боя.

- В меню новой игры — режим «Тестирование»: выбор карты (размер, сид,
  пустое поле для чистого боя) и состава обеих сторон — количество каждого
  типа юнита и зданий, стартовые ресурсы. Состав задаётся числами, без
  расстановки по одному.
- Расстановка автоматическая и воспроизводимая: стороны у своих баз, юниты
  на свободных проходимых клетках (летающие — где угодно). Опционально —
  ручная правка расстановки кликом, переиспользуя команды отладки S02a.
- Управление каждой стороной: человек, ИИ или «пассивная» (пропускает ход).
  ИИ против ИИ с ускоренным ходом и паузой — основной сценарий баланса.
- Итог боя: победитель, число ходов, потери и нанесённый урон по типам,
  оставшиеся ресурсы; выгрузка в JSON для сравнения прогонов. Тот же сценарий
  запускается headless-тестом (как `scripts/ai-match-smoke.test.ts`) по списку
  сидов, чтобы сравнивать баланс до/после правки числами.
- Режим помечен как тестовый (как «Отладка»): не влияет на сохранения обычных
  партий и статистику, туман можно отключить отдельно.

**Подсказки:** сценарий — это данные (карта + составы + контроллеры), один
формат для UI и headless-прогона; не дублировать логику старта партии.
**Unit-тесты:** проверка состава (лимиты, неизвестный тип, нулевые
значения), воспроизводимая расстановка по сиду, подсчёт итогов боя.

**Готово:** любой состав обеих сторон ставится за минуту без консоли;
бой ИИ против ИИ по сидам даёт сравнимый числовой итог.

## S15b. Исполнитель и распределение нагрузки хода ИИ

**Состояние:** реализовано. `runAITurn` держит один запуск на партию, ход и
участника (повторный вызов возвращает тот же Promise); пауза режима
тестирования ждёт в `playTurn` перед шагом (`waitWhilePaused`), сброс и конец
партии прекращают ожидание. Порция — `AI_CONFIG.yieldBudgetMs` (8 мс) по
`performance.now()`, перерыв — `AI_YIELD_BREAK_MS` (16 мс), в режиме «Быстро» —
`setTimeout(0)`. Пауза проверяется и перед завершением хода; запуск
регистрируется до начала хода, поэтому повторный вход из подписчика стора
получает тот же Promise. Равные оценки в `decideStep` разрешаются по ключу
с типом и клеткой объектов вместо случайных ID.
Проверено: unit (`playTurn.test.ts` — бюджет порции, пауза продолжает тот же
ход, пауза после последней команды не завершает ход, отмена во время паузы;
`decide.test.ts` — выбор не зависит от ID), интеграционно
(`sandbox.integration.test.ts` — пауза и продолжение, сброс во время паузы,
повторный вызов и повторный вход из подписчика, вызов после конца хода,
одинаковый бой по сиду при разной скорости отдачи управления). Браузер:
пауза посреди хода на 100×100 держит ход, «Продолжить» доигрывает его.

**Замеры** (`AI_TIMING=1 pnpm vp test run scripts/ai-turn-timing.test.ts`:
ИИ против ИИ, у стороны 18 военных юнитов и 7 зданий плюс ратуша и рабочий,
сид 7, 8 полных раундов; порция — время вычислений между отдачами
управления, без перерывов; одна машина):

| Карта   | Самая длинная порция: до → S15b → после оптимизаций |         Средний ход |     Самый долгий ход |
| ------- | --------------------------------------------------: | ------------------: | -------------------: |
| 40×40   |                                     59 → 14 → 13 мс |     91 → 82 → 24 мс |   409 → 382 → 100 мс |
| 100×100 |                                    388 → 39 → 31 мс | 1054 → 401 → 125 мс | 2236 → 1918 → 441 мс |

Бюджет прерывает только между шагами, поэтому порция не короче шага.
Длительность хода «до» и «после» не строго сравнима: решения ИИ меняются
вместе с исправлениями. В браузере добавляются перерывы 16 мс между
порциями; в фоновой вкладке браузер растягивает `setTimeout` до 1 с, и ход
ИИ там идёт медленнее.

После S15b (оптимизации):

- **Цикл W06 ↔ W02.** Рабочий, снятый с добычи под ферму, выходил прямо на
  её площадку; задача стройки считалась закрытой («площадка занята»), и W02
  возвращал его в рудник — до предела 80 команд. Это было 40–50% всех
  решений ИИ. Теперь исполнитель на площадке не закрывает свою задачу
  (`memory.ts`), рабочий отходит и строит ферму.
- **Поиск пути** `findCheapestPaths` идёт по типизированным массивам
  (результат и порядок клеток прежние; эквивалентность — `terrain.test.ts`),
  примерно в 1,6 раза быстрее.
- **W10** кэширует на шаг сетку «свои проходимы» для поиска мешающего
  юнита. Предфильтр «рядом есть клетка ближе к цели» пробовали и убрали:
  по ревью он пропускал ~4% реальных застреваний (тупиковый карман рядом
  с коридором; регрессионный тест в `passage.test.ts`). W10 остаётся самым
  тяжёлым правилом (до ~25 мс за вызов на 100×100), затем C05: основная
  цена — пути юнитов группы, которые затем из кэша шага берут и другие
  правила. Время правил — в выводе `scripts/ai-turn-timing.test.ts`
  (`heaviestRules`).
- **Зависания отрисовки.** На 100×100 при камере «Вся карта» браузер
  замирал на ~1,2 с, когда наблюдающая сторона разведывала клетки: кэш
  рельефа перерисовывал весь видимый мир, а браузер заново растеризовал
  его. Теперь перерисовываются только тайлы вокруг изменений
  (`terrainCache.ts`, тест `terrainCache.test.ts`). Проверено в браузере:
  частичная и полная перерисовка совпадают пиксель в пиксель (5 сцен,
  дробные масштабы, сдвинутый диапазон с изменениями за его краем); в бою ИИ против ИИ на 100×100 при
  масштабе 28% за 15 с — ни одной задачи длиннее 50 мс (было четыре по
  ~1,2 с), в production-сборке так же.

Зависимости: S15a (замеры в режиме тестирования). Выполнить до S17: профили
и сложность S17–S17a добавят ИИ работы, а интерфейс не должен замирать.

Было до S15b: `runAITurn` асинхронный, `playTurn` отдавал управление браузеру
каждые 8 шагов (`setTimeout(0)`). Повторный запуск того же хода возвращал
`null`, пауза отменяла идущий ход, а «Продолжить» планировал его заново.
На огромной карте восемь дорогих шагов подряд блокировали интерфейс.

Два отдельных патча, в этом порядке — иначе ускорение и пауза усилят гонку
запусков:

1. **Один управляемый исполнитель хода.**
   - Один активный запуск на партию, участника и номер хода: повторный вызов
     для того же хода возвращает существующий Promise, а не `null`. Сброс
     партии отменяет старый запуск.
   - Пауза — часть исполнения: `playTurn` перед очередным шагом ждёт
     разрешения продолжить, сохраняя память хода и текущий шаг; продолжение
     возобновляет тот же цикл, а не планирует ход заново. Сброс или конец
     партии прекращают и ожидание.
   - В `Game.tsx` смена `paused` и `fast` не создаёт новый исполнитель:
     пауза приостанавливает его между действиями, скорость меняет задержку.
2. **Бюджет времени вместо «каждые 8 шагов».**
   - Через `performance.now()` мерить время с последнего перерыва; после
     завершения действия, если прошло около 8 мс, отдавать управление
     браузеру. Следующее наблюдение собирать после ожидания — оно остаётся
     актуальным.
   - Разделить порцию вычислений и перерыв. Стартовые значения для замеров:

     | Режим   | Порция вычислений | Перерыв         |
     | ------- | ----------------: | --------------- |
     | Обычный |        около 8 мс | 16–32 мс        |
     | Быстрый |        около 8 мс | `setTimeout(0)` |

   - Не добавлять задержку каждому юниту и не гарантировать минимальную
     длительность всего хода: маленькая армия заканчивает быстро, большая —
     постепенно.

Ограничение: асинхронность не уменьшает объём вычислений, паузы только
распределяют их во времени. Если один шаг планировщика (например, поиск
пути) сам занимает сотни миллисекунд, внешняя разбивка его не прервёт —
тогда оптимизировать этот расчёт или вынести планировщик в Web Worker.
Worker пока отложить до замеров.

Попутно (связано с «скорость не меняет решения»): равные оценки ИИ
разрешались по ключу действия со случайными ID объектов, поэтому одинаковый
сид давал разные бои. Сделано: разрешение равенства не зависит от ID,
прогоны S15a воспроизводимы.

**Unit/интеграционные тесты:** повторный запуск не дублирует команды; на
паузе команды не выполняются; продолжение сохраняет ход и его память; сброс
во время ожидания останавливает старую партию; скорость не меняет решения
ИИ; одинаковый сценарий и сид дают одинаковый бой.
**Замеры:** на огромной и гигантской карте — длительность всего хода и самой
длинной непрерывной порции, до и после; записать в этот раздел.

**Готово:** интерфейс отзывчив во время хода ИИ на самой большой карте
(самая длинная порция — около бюджета, если один шаг не дороже); пауза и
скорость не порождают второй ход; бой воспроизводим по сиду.
