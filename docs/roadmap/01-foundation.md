## S01. Зафиксировать правила и проверочные сценарии

  в S08; правило осады, если выбрано, подключить в S14–S15. Это отдельное действие,
  не автоматическое утверждение истощения ресурсов D02.

- Зафиксировать обязательный подготовленный удар осады S14: выбор клетки сейчас,
  удар на следующем своём ходу, отмена при уничтожении орудия.
  Определить цену/очки, дальность, момент исполнения относительно обновления
  наблюдения и приказов S19, урон своим и допустимые цели, включая воздух.
  Отметка и её снятие публичны по контракту MVP; они не раскрывают
  положение орудия. Исключение — «Скрытая наводка» S16. Числа подобрать в S21.

- Для двух сторон победа — уничтожение чужой ратуши; поражение — потеря своей
  или сдача. Общие правила выбывания и исхода нескольких сторон — в S01a.
- Согласовать контракты участников/отношений, рас и сложности из
  [S01a](01-foundation.md) и [S17a](09-ai-profiles-and-difficulty.md), типы урона, лечение и полёт из
  [S14a–S14b](06-magic-and-flight.md). Подробный контент делать в указанных шагах.
- Для S19 согласовать пропуск/удержание и приказы движения на несколько ходов;
  для S20 — слоты, интервалы и ротацию автосейва.
- Предлагаемый порядок хода: выполнить активные приказы движения S19 →
  при остановке вернуть управление, иначе завершить действия → начислить доход → продвинуть
  исследования владельца → определить исход → передать ход → восстановить
  очки только новой активной стороны → исполнить подготовленные удары осады →
  определить исход → обновить её наблюдение.
- Найм/постройка мгновенны; новый юнит действует со следующего своего хода.
  После атаки/строительства движение заканчивается. Башней управляет владелец.
- Подготовить unit-окружение по [плану тестирования](../unit-testing.md): один
  раннер, одиночный запуск, фильтр файлов, TypeScript и алиасы. Начать с существующих
  расчётов/проверок; тесты новых правил добавлять в шаге их реализации.
- Сценарии взаимодействия хранилищ и целой партии вести отдельно от unit-тестов:
  наличие тестового запуска само по себе не подтверждает победу/поражение.
- Зафиксировать исходные результаты type-check, lint, build; существующие ошибки
  исправлять отдельными ограниченными изменениями, не скрывать в новом коде.

**Подсказки:** начни с таблицы «вход → наблюдаемый результат → запрет» для правил.
Для первого тестового запуска удобнее расчёт стоимости, чем партия с Canvas;
выбор раннера сравни по совместимости с текущей сборкой и простоте запуска.
**Unit-тесты:** недостаток/точное количество ресурсов, пустой доход, сумма населения;
проверить, что раннер находит тесты, а ошибочное ожидание действительно роняет запуск.

**Готово:** правила не противоречат друг другу; unit-запуск работает из чистой
установки, есть первые тесты расчётов и список сценариев для S02–S03.

**Результат S01:** правила, контракты и сценарии S02–S03 — в

уже были в репозитории; базовые проверки зелёные, падающий тест роняет запуск.

## S01a. Участники без ограничения на две стороны

Зависимости: S01. Выполнить до S02–S04 и до проектирования наблюдений S06.

- Разделить идентификатор участника и способ управления им: человек или ИИ.
  Несколько ИИ — разные участники, со своими ресурсами, населением, исследованиями,
  знаниями, памятью, задачами, настройками и состоянием случайного выбора.
- Владельцем объекта является участник. «Свой» для интерфейса определяется
  относительно управляемого участника, а не строкой `player`; враг не равен `ai`.
- Задать список участников и порядок ходов. Выбывшие пропускаются; доход, очки,
  исследования и эффекты относятся к конкретному ходу владельца.
  Полный круг завершается после обхода оставшихся участников.
- Предложение для игры без союзов: потеря ратуши/сдача выводит участника;
  оставшиеся его объекты удаляются без добычи и посмертных действий.
  Матч заканчивается, когда остался один участник.
  Потеря человека показывает поражение и позволяет выйти, не объявляя одного
  из нескольких ещё живых ИИ победителем всей партии.
- Поиск целей должен возвращать всех допустимых противников. Заранее отделить
  отношение «свой / союзный / враждебный» от проверки владения:
  союзник в будущем не получает право отдавать приказы чужим юнитам.
  Пока все разные участники враждебны; дипломатия и интерфейс союзов не нужны.
- Генерация получает число и позиции стартов; проверяет ресурсы, расстояния,
  отсутствие наложений и связность наземных подходов для каждого участника.
  Неподдерживаемые сочетания размера/числа сторон отклонять до запуска.
- Уже здесь выбрать, что меняется при выбывании стороны: её очередь, рабочие
  назначения, резервы, источники обзора и контакты в чужой памяти.
  Скрытая потеря объектов не должна раскрывать их координаты через туман.

**Подсказки:** сначала найди места, где «другая сторона» вычисляется переключением
между двумя значениями. Проведи один третий ID через команды и цикл ходов,
затем через генерацию и знания. Не нужен сетевой код, произвольные контроллеры
или универсальная дипломатическая система ради одного локального матча.
Для отношений достаточно одного согласованного места проверки.

**Unit-тесты:** очередь из трёх сторон, пропуск выбывшей, граница круга,
однократный доход, независимость ресурсов/настроек двух ИИ, отказ чужого приказа,
несколько врагов, исход при одном/нуле оставшихся. Интеграционно — три базы,
выбывание одной стороны без преждевременного завершения и сброс такой партии.

**Результат S01a:** владелец — ID слота `p1`–`p4` с управлением человек/ИИ;
очередь, пропуск выбывших, круг, выбывание с удалением объектов, исход
(победитель, ничья, поражение человека без победителя) и отношения в одном
месте. Интерфейс определяет «своё» через управляемого участника. Тесты:
очередь на троих, выбывание, ничья одним действием; интеграционно — три базы,
доход одному, цели по двум врагам, чужой приказ, сброс. Генерация S04 уже
принимает 2–4 участников и отклоняет слишком маленькую карту до создания объектов.

**Готово S01a:** модель участников и сценарий очереди с тремя ID не требуют
специальной ветки для третьего владельца. Пока команды задаёт тестовый сценарий.
Генерацию и полный жизненный цикл довести в S03–S04, знания — в S06, независимый
запуск двух ИИ — в S09; итоговую сцену на троих принять в S21–S22.
Это проверка основы, а не обещание сбалансированного режима на любое число участников.

## S02. Общие игровые команды

Зависимости: S01a. Ориентиры: `features/build`, `spawn`, `combat`, `pathfinding`,
`entities/units/model/unitsStore.ts`, `widgets/map/ui/utils/mapClickHandler.ts`.

- Вводить явные параметры: действующая сторона, ID исполнителя, тип создаваемого
  объекта, цель/координаты. Команда не читает выбранный объект интерфейса.
- UI и ИИ вызывают одни действия: движение, атака, строительство, найм,
  завершение хода; позже — назначение рабочего, исследование и лечение.
  Владение, отношения и данные команды привязаны к ID участника, не к виду управления.
- Перед изменением состояния проверять фазу, владельца, активный ход, существование
  объектов, границы, занятость, местность, допустимый тип, расстояние/путь,
  очки действий, ресурсы и население. В S06 добавить проверки видимости.
- Списывать ресурсы именно действующей стороны. Невалидная команда ничего
  не меняет и возвращает причину; проверка и применение не разделены ожиданием.
- Рассчитывать достижимость и стоимость движения по одному пути, а не Manhattan
  между концами. Наземные юниты не проходят сквозь занятые клетки и не встают
  на здание. Правила транзита/остановки воздуха расширяются в S14b.
- Поиск врагов получает сторону явно; служебное создание стартовых объектов
  отделено от платного найма и не является обходом правил для ИИ.
- Сохранить текущие хранилища; не переписывать всё приложение ради нового API.

**Подсказки:** проследи один приказ от клика до изменения хранилища, затем сравни
его с потребностями ИИ. Можно выделить проверку отдельно или оставить рядом с
применением; оцени риск расхождения предпросмотра и реального выполнения.
**Unit-тесты:** по одному правилу отказа на случай; на границе хватает/не хватает
очков и цены. Проверять результат и неизменность состояния при отказе.

**Готово:** одинаковая команда даёт одинаковый результат из UI и из сценария ИИ.
**Проверить:** чужой юнит, чужой ход, занятая клетка, недостаток ресурсов,
неподходящее здание найма, обход препятствия, отказ без частичного списания.

**Результат S02:** команды `move`, `attack`, `build`, `spawn`, `nextTurn` принимают
объект с `actor` и явными параметрами (тип здания/юнита больше не берётся из
выбора UI), проверяют правила по порядку и возвращают `CommandResult` с кодом
отказа (`shared/config/commands.ts`). Клик по карте передаёт команды через
`MapClickContext`; ИИ вызывает `nextTurn(actor)`. Журнал `entities/journals`
хранит события и ошибки партии, ошибки старта идут туда же. `getPatch.ts` →
`getPath.ts`, `calculateMovement` → `calculateActionHighlights`; `currentPath`
к этому моменту уже отсутствовал. Показ ошибок игроку — S19. Тесты: отказы
по каждому правилу с неизменностью состояния, точная цена, клик и сценарная
команда дают одинаковый итог, журнал (повтор, сбой, партии, лимит, видимость).
`runCommand` отклоняет вложенные приказы кодом `busy`, пока текущая команда
не закончила изменения и списания. Регрессионный сценарий: подписчик создания
юнита пытается нанять второго при ресурсах ровно на одного — второй не создаётся,
остаток ресурсов равен нулю. Это защита повторного входа, не откат произвольного
исключения после изменения store.

### Упрощение пути команды и подсветки

- В `Map.tsx` и `mapClickHandler.ts` заменить 14 позиционных аргументов небольшим
  объектом с именованными полями. Выделить понятный сброс интерактивного выбора;
  сохранить различия очистки выбора, стройки и найма и приоритет веток клика,
  включая атаку башни. Map переводит клик в намерение, команда возвращает результат,
  UI обновляет выбор/сообщение. Неиспользуемый boolean убрать либо явно использовать
  как «клик обработан»: это не то же самое, что «команда выполнена».
  Изменение очистки после отказа рассматривать отдельно от рефакторинга.
- Передавать тип в `build`/`spawn` явно, сохранив отдельные команды и проверки.
  Выделять общую валидацию только при совпадении правил: ресурсная постройка
  и найм на свободном поле/холме имеют разные требования. Болото проходимо,
  но не является полем для найма по контракту S01.
- Удалить неиспользуемый `currentPath` из `movementStore`; контракт автодвижения
  появится по реальной потребности S19. Переименовать `calculateMovement(unitId)`
  по ответственности, например в `calculateActionHighlights(entityId)`, поскольку
  он считает и цели башни. `getPatch.ts` переименовать в `getPath.ts`, обновив
  импорты и тест; публичный экспорт `getPath` сохранить.

**Подсказки:** делать вместе с явными командами, без временного диспетчера,
плагинов или базового класса. Сохранять отдельные действия, store, роли объектов,
публичные экспорты и клонирование сетки поиска пути; алгоритмы не переписывать
ради краткости или новой зависимости.
**Результат:** контекст клика (`MapClickContext`, отдельный файл) сгруппирован
по ролям: `clicked`, `selection`, `highlights`, `commands`, `ui`. Сборка контекста
вынесена из `Map.tsx` в хук `useMapCellClick`. Полный сброс — `resetInteraction`;
выбор объекта под курсором по-прежнему не снимает подсветку стройки/найма сам.
Лишняя очистка после найма удалена: `clearSelection` уже сбрасывает выбранные
типы стройки и найма. Неиспользуемого boolean к этому шагу уже не было; итог
команды пока не влияет на очистку выбора. Тесты: атака юнитом, стройка
выбранным типом, клик без выбранного типа, одинаковый сброс при отказе команды.

**Проверки/готово дополнительно для S02:** повторный клик, выбор врага, движение,
атаки башни/юнита, стройка, найм и отказ сохраняют порядок обработки и подсветку.
Одинаковая команда не зависит от UI-выбора; чужой ход/объект, неверный тип,
занятость и нехватка средств не меняют состояние. Импорты и экспорты согласованы.

### Единые ошибки и журнал (D07–D08)

- Реализовать общий путь ошибок команд и старта, далее подключать новые источники.
  Различать ожидаемый отказ и сбой; русский текст для игрока не раскрывает скрытый
  мир, технические детали доступны отладке. Выбрать необходимость отдельного store,
  ограничение повторов и очистку между партиями; ошибка не портит состояние.
- Реализовать единый механизм записи/хранения событий: ID партии, ход, участник,
  тип и снимок доступных сведений. Действия игрока поступают в обычный журнал;
  полные события врага — только в отладочный. Видимые последствия вражеских
  действий разрешены обычному журналу по правилам тумана S06.
- Ограничить объём истории; не создавать параллельные журналы для UI и ИИ.
  Ошибка может ссылаться на событие, но запись не заменяет обработку отказа.

**Подсказки:** переиспользовать существующие события и подключать потребителей
по этапам: ИИ S09–S10, UI S19, сохранение/диагностика S20.
**Unit-тесты:** повтор ошибки, очистка без изменения игры, изоляция партий,
лимит записей, отказ без изменения состояния, отсутствие скрытых данных
в пользовательской записи.
**Результат:** общий путь ошибок и журнал сделаны вместе с командами S02
(`entities/journals`, `runCommand`). Здесь добавлены последствия команд —
`unitDestroyed`, `buildingDestroyed`, `eliminated`, `gameOver` — из игровых
событий (`app/system/journal.ts`) и явная видимость записи `visibleTo`,
которую в S06 будет вычислять туман. Отдельного store ошибок нет: они в том же
журнале. Пока гибель своего юнита показывает, какой участник атаковал; скрыть
это под туманом — S06. Ссылка ошибки на событие не понадобилась. Тесты:
видимость атаки и гибели сторонам, чужие приказы вне обычного журнала,
выбывание и исход для всех, очистка ошибок без изменения игры, новая партия.

**Готово дополнительно для S02:** команды и старт используют общий путь ошибок
и событий; последующие этапы расширяют его, а не добавляют независимые системы.

## S02a. Основа режима отладки

Зависимости: S01a, S02. Реализовать после общих команд, до массового наполнения
игры. Полный обзор подключить в S07, журнал решений ИИ — в S09–S10.

- Явное включение режима и постоянно видимая отметка «Отладка».
  По умолчанию все переключатели выключены; режим не является уровнем сложности.
- Отдельные переключатели: бесплатное строительство, строительство за один ход,
  бесплатный найм. Выбирать участника, для которого они действуют, по ID:
  человек, конкретный ИИ или явно все участники.
- Бесплатность отменяет проверку и списание цены, но сохраняет население,
  очки действий, владельца, активный ход, подходящий тип здания/юнита,
  местность, занятость и границы. Предпросмотр цены согласован с исполнением.
- «За один ход» означает завершить постройку в ход команды без ожидания
  последующих ходов. В текущих правилах строительство уже мгновенно:
  сохранить это поведение, не вводить очередь только ради переключателя.
  Если сроки строительства появятся позже, переключатель сокращает их.
  Бесконечные очки и немедленные действия новобранцев сюда не входят.
- Применять исключения через общий путь команд с явным контекстом отладки;
  не менять глобальные цены и базовую конфигурацию. Отклонённая команда
  по-прежнему ничего не создаёт и не тратит.
- Переключать настройки между командами; в журнале отмечать участника,
  ход и использованные исключения. Сброс партии выключает переключатели.
  Отключение режима возвращает обычные правила для следующих команд,
  но не удаляет уже построенное и не списывает его стоимость задним числом.
- Партия сохраняет признак использования отладки даже после её выключения.
  Такие партии не включать в обычную приёмку баланса/честности ИИ S21.

**Подсказки:** сначала проверить бесплатную команду на маленькой сцене с нулём
ресурсов, затем подключить панель. Не дублировать создание объектов:
население, события и рабочие назначения должны обновляться обычным способом.

**Unit-тесты:** режим выключен, бесплатная команда при нуле ресурсов, независимые
настройки двух ИИ, занятая клетка/нехватка населения, обычная цена после выключения,
постройка готова в текущем ходу, сброс настроек без изменения базовой конфигурации.

**Результат S02a:** режим включается в «Меню», пока он включён, в шапке видна
отметка «Отладка», а в правой панели — исключения для выбранного участника
(«Вы», конкретный ИИ или «Все участники»). Хранилище `useDebugStore` лежит
в `entities/settings`. Команды `build`/`spawn` берут исключения участника
через `getDebugExceptions`, цену проверяют через `getPayableResources` — тот же
расчёт показывает карточка. Использованные исключения пишутся в журнал
(`details.debug`). «За один ход» пока только отмечается: стройка и так
мгновенна. Признак `usedInGame` держится до сброса партии; сброс выключает всё.

**Готово S02a:** панель включает бесплатную стройку/найм для выбранной стороны,
строительство завершается за один ход, обычные команды сохраняют прежние правила.
Полный режим принимается после подключения тумана S07 и решений ИИ S10.

## S04. Воспроизводимая карта без тупиков на старте

Зависимости: S02–S03. Ориентиры: `generateMap`, `prepareStartArea`, `initializeGame`.

- Все случайные решения генерации, включая золото, брать из одного генератора
  с сидом. Показывать сид партии; случайный режим сначала выбирает этот сид.
- После всех изменений рельефа и размещения баз проверить свободные выходы,
  путь между подходами к базам и доступ рабочего к соседней клетке ресурса.
- Каждый участник должен иметь доступ к лесу и золоту в сопоставимом стартовом
  расстоянии. Проверять подходы, а не непроходимую клетку самого ресурса.
- Ограничить попытки генерации. При неудаче применять проверенную резервную
  раскладку либо показывать понятную ошибку; не запускать заведомо плохую карту.
- Фиксированный сид проходит те же проверки. Воспроизводимость включает
  итоговую резервную раскладку и версию генератора.
- Применять стартовые условия S17a один раз для каждого ID участника;
  число баз и размещение брать из состава партии S01a, не из двух углов.
- Завести набор сидов: открытое поле, узкий проход, мало ресурсов, края карты;
  проверить все поддерживаемые размеры. Большие размеры добавлять через S05.

**Подсказки:** рассмотри раздельную генерацию и проверку результата: плохую карту
тогда можно разобрать независимо от случайности. Для равенства стартов сравни
длину доступных подходов, а не расстояние до ресурса по прямой.
**Unit-тесты:** одинаковый сид, недопустимые размеры, ресурс без подхода,
разорванный маршрут и достижение лимита попыток; массовые сиды запускать отдельно.

**Готово:** одна версия генератора + настройки + сид дают одну карту; каждый
принятый старт имеет выходы, ресурсы и путь к противнику.
**Проверить:** минимум 100 сидов на каждый текущий размер и отдельные плохие сиды.

### Оценка подготовленной карты (часть S04)

Из `initializeGame.ts` вынести проверку карты с явными входами `grid` и стартовыми
позициями и результатом с причиной отказа. Отдельно назвать проверку доступного
подхода к ресурсу; учитывать будущую занятость ратушами и подход к золоту/лесу.
Ограниченный цикл попыток и создание объектов оставить в оркестраторе старта.
**Подсказки:** чистую оценку использовать и в smoke-прогонах; класс генератора
и многоступенчатый конвейер не нужны. Равенство расстояний до ресурсов проверять
как отдельное расширение правил, не как следствие структурного упрощения.
**Unit-проверки/готово дополнительно для S04:** путь между стартами есть/нет,
ресурс без подхода, воспроизводимый сид, лимит попыток и отказ без создания объектов.
