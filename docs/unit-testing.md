# Unit-тестирование: первый этап

Установлен Vitest. Тесты работают в Node с алиасами из Vite, без DOM
и браузера.Полный S01 ещё требует согласовать правила MVP.

## Запуск

- `pnpm test` — весь набор.
- `pnpm test:unit` — только unit-тесты.
- `pnpm test:integration` — взаимодействие настоящих хранилищ и событий.
- `pnpm test:unit -- src/features/pathfinding/lib/getPath.test.ts` — один файл.
- `pnpm type-check` — отдельная проверка типов, включая тесты.

Unit-тесты размещаются рядом с модулем в `*.test.ts`. Интеграционные сценарии
имеют суффикс `*.integration.test.ts` и исключены из unit-команды.
Сейчас покрыты воспроизводимость генерации, границы и повторный поиск пути,
преобразования камеры и мини-карты, обзор, знания и контакты сторон, сцена
карты под туманом; интеграционно — строительство, найм, бой, движение под
туманом, наблюдения участников, завершение и запуск партии.
Правила ИИ проверяются на маленьких сценах из наблюдения
(`features/ai/lib/scene.test-utils.ts`): каждому W/X/N/M/A/T/G-правилу —
срабатывание и отказ; отдельно выбор стратегии с удержанием, веса и
разрешение равных оценок, операции ударной группы, задачи и резервы, цикл
хода с подменёнными командами. Интеграционно — отмена устаревшего хода ИИ
и раздельная память и журнал двух ИИ.
Браузерная проверка Canvas выполняется отдельно и не заменяется этим набором.

Не нужны общий coverage-порог, браузерные зависимости или собственный фреймворк.
Новые проверки добавляются для реализованных правил и воспроизведённых ошибок.

## Что покрывать сначала

| Существующий модуль      | Полезные случаи                                                                                     |
| ------------------------ | --------------------------------------------------------------------------------------------------- |
| `canSpawnUnit`           | Ресурсов/населения ровно хватает и на единицу меньше; очки найма 0; необязательные очки не переданы |
| `canSpawnBuilding`       | Дефицит каждого ресурса отдельно; очки строительства; точная цена                                   |
| `calculateIncome`        | Пустой список, разные доходы, отсутствие изменения входных данных                                   |
| `calculateMaxPopulation` | Сумма снабжения, пустой список, здание без снабжения; общий предел 30 применяется в другом месте    |

Затем — маленькие проверки команд, маршрутов и переходов одного хранилища.
Исследования покрываются при появлении их реализации.
Не писать тесты к вымышленным функциям из будущих этапов roadmap.

## Границы unit-уровня

- Проверять одну функцию, правило или изолированное действие модуля через его
  результат/изменение состояния. Данные — маленькая сцена, достаточная для условия.
- Сброс глобальных хранилищ, отписка событий, восстановление подмен времени/случайности
  обязательны там, где тест ими пользуется; порядок тестов не должен влиять на итог.
- Связка нескольких настоящих хранилищ и событий — интеграционный сценарий.
  Полная партия, внешний вид тумана, фокус и камера в браузере — отдельные проверки.
- Не заменять всю игровую логику моками: такой тест доказывает только настройку моков.
  Не копировать алгоритм в ожидание и не закреплять известный дефект как норму.
- Для каждого нового шага брать unit-случаи из его раздела, но подтверждать
  ожидаемое поведение реализованным контрактом или явно принятым правилом.
