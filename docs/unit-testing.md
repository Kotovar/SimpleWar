# Unit-тестирование: первый этап

Статус: план подготовки S01. Сейчас в `package.json` нет тестового раннера
и команды тестов. Этот документ и скил не означают, что тесты уже установлены.

## Что добавить в S01

- Один раннер для TypeScript, одиночный запуск всего unit-набора и фильтр файлов.
  Кандидат — Vitest: проверить совместимость выбранной версии с Node и текущим
  `vite` → `rolldown-vite`, не обновлять сборщик ради тестов без необходимости.
- Для логики достаточно среды Node; DOM, Canvas, браузер и dev-сервер не нужны.
  Использовать имеющиеся алиасы. Отдельная тестовая конфигурация не должна
  незаметно потерять настройки разрешения импортов из Vite.
- Сначала проверить реальный модуль с алиасом, затем один полезный тест границы
  правила. Пустой запуск, который «прошёл» без тестов, не закрывает S01.
- Предлагаемое имя команды — `test:unit`, работающей без watch. Если выбран Vitest,
  ей соответствует `vitest run`; фильтр передаётся после `--` через npm.
- TypeScript проверять отдельно: выполнение тестов не заменяет проверку типов.
  При размещении тестов вне `src` обеспечить их включение в проверку TypeScript.
- Сохранить существующий менеджер пакетов и выбранный проектом lockfile.
  Здесь есть оба lockfile: не синхронизировать и не удалять их попутно;
  перед установкой определить используемый по настройкам/инструкции пользователя.
  Если выбор не закреплён, использовать npm, как в текущей документации проекта,
  и обновлять только `package-lock.json`.
- В этой подготовке не требуются coverage-порог, браузерные зависимости,
  собственный тестовый фреймворк или массовая переработка игрового кода.

По конфигурации и одиночному запуску сверяться с
[руководством Vitest](https://vitest.dev/guide/) и
[справкой конфигурации](https://vitest.dev/config/), а не фиксировать здесь версию.

## Что покрывать сначала

| Существующий модуль      | Полезные случаи                                                                                     |
| ------------------------ | --------------------------------------------------------------------------------------------------- |
| `canSpawnUnit`           | Ресурсов/населения ровно хватает и на единицу меньше; очки найма 0; необязательные очки не переданы |
| `canSpawnBuilding`       | Дефицит каждого ресурса отдельно; очки строительства; точная цена                                   |
| `calculateIncome`        | Пустой список, разные доходы, отсутствие изменения входных данных                                   |
| `calculateMaxPopulation` | Сумма снабжения, пустой список, здание без снабжения; общий предел 30 применяется в другом месте    |

Затем — маленькие проверки команд, маршрутов и переходов одного хранилища.
Туман, память, правила ИИ и исследования покрываются при появлении их реализации.
Не писать тесты к вымышленным функциям из будущих этапов roadmap.

## Границы unit-уровня

- Проверять одну функцию, правило или изолированное действие модуля через его
  результат/изменение состояния. Данные — маленькая сцена, достаточная для условия.
- Сброс глобальных хранилищ, отписка событий, восстановление подмен времени/случайности
  обязательны там, где тест ими пользуется; порядок тестов не должен влиять на итог.
- Связка нескольких настоящих хранилищ и событий — интеграционный сценарий.
  Полная партия, внешний вид тумана, фокус и камера в браузере — отдельные проверки.
- Не заменять всю игровую логику моками: такой тест доказывает только настройку моков.
  Не копировать алгоритм в ожидание и не закреплять известный дефект как норму.
- Для каждого нового шага брать unit-случаи из его раздела, но подтверждать
  ожидаемое поведение реализованным контрактом или явно принятым правилом.

## Запрос небольшой локальной модели

Скил хранится в репозитории: [simplewar-unit-tests](../skills/simplewar-unit-tests/SKILL.md).
Он указан в `AGENTS.md`; глобальная установка и распознавание `$имени` не требуются.
Модели с доступом к файлам достаточно прямого запроса:

> Прочитай AGENTS.md и skills/simplewar-unit-tests/SKILL.md.
> Напиши unit-тесты для src/shared/lib/canSpawnUnit.ts и
> src/shared/lib/canSpawnBuilding.ts. Выполни тесты и покажи результат.

Можно передавать папку вместо файлов. Если у модели нет доступа к файловой системе,
передай ей скил, целевые исходники, прямые зависимости и тестовую конфигурацию;
без инструмента запуска она должна сообщить, что тесты не выполнялись.

После подготовки раннера запуск будет, например,
`npm run test:unit -- src/shared/lib/canSpawnUnit.test.ts`.
**Сейчас эта команда ещё не добавлена.** Фактическую команду закрепить после S01.
