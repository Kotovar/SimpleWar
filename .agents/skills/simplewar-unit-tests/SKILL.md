# Unit-тесты для SimpleWar

Вход: пути файлов/папок из запроса. Результат: небольшие работающие unit-тесты
этого кода и честный отчёт запуска. Пиши тесты, не новые скилы и не будущие механики.

## 1. Прочитай ровно нужный контекст

- Прочитай корневой `AGENTS.md`, `package.json` и тестовую конфигурацию.
  Сохрани существующие изменения пользователя; не делай commit/stage.
- Найди целевые функции, прямые зависимости, их вызовы и ближайшие тесты.
  Предпочитай граф кода; если он недоступен/неполон, используй `rg` и чтение файлов.
- Папку разбирай небольшими порциями до завершения запроса; не загружай весь проект.
  Пропускай переэкспорты и стили без логики, в отчёте объясни непокрытые части.
- Выпиши для каждой выбранной функции вход, результат/эффект и значимые границы.
  Roadmap описывает будущее: не выдумывай по нему ещё отсутствующий API.

## 2. Проверь окружение

- Используй существующий раннер и соглашения. Если их нет, подготовь минимальный
  запуск по [docs/unit-testing.md](../../docs/unit-testing.md) в рамках задачи тестов:
  один совместимый раннер, команда, алиасы и проверка типов тестовых файлов.
- Не устанавливай второй раннер; не запускай скачивание неизвестной версии через
  голый `npx`. Не меняй версии приложения и не отключай проверки ради запуска.
- Если среду нельзя подготовить из-за доступа/совместимости, укажи точную причину;
  не называй непроверенные тесты работающими. Если инструмента запуска нет — так и скажи.

## 3. Напиши тесты поведения

- Используй существующее размещение; если соглашения нет — `имя.test.ts` рядом
  с модулем. Импортируй реальную функцию, не переписывай её внутри теста.
- Начни с успешного случая, добавь значимые отказы и границы: ровно хватает,
  на единицу меньше, пустой список, ноль действий — только применимые к контракту.
- Один тест проверяет одну причину. Для отказа по населению обеспечь достаточно
  ресурсов и очков, иначе проверишь другую ветку. Ожидания вычисляй независимо.
- Проверяй результат и нужные изменения/отсутствие изменений. Не проверяй приватный
  порядок вызовов, случайные ID или точный текст, если это не часть контракта.
- Используй реальные типы и минимальные данные. Не скрывай ошибки через `any`,
  двойные приведения, `@ts-ignore`, пустые проверки или огромные snapshots.
- Подменяй только внешние зависимости. Не мокай проверяемую функцию и всю цепочку
  её расчётов. Случайность/время фиксируй при необходимости, реальные ожидания не нужны.
- Для Zustand сбрасывай данные перед каждым тестом, сохраняя методы хранилища;
  не полагайся на неполный `resetStore`. Отписывай свои обработчики событий,
  восстанавливай моки/таймеры. Тест не зависит от предыдущего запуска.
- Не подключай UI, Canvas, сеть или целую партию ради unit-теста. Если модуль
  без них не изолируется, опиши границу; рефакторинг production-кода требует
  отдельной задачи, не меняй его только для удобства тестирования.
- Найденный дефект не закрепляй как правильный результат. Если ожидаемое поведение
  установлено — оставь воспроизводящий тест и сообщи о падении; если контракт
  неоднозначен — опиши неопределённость, не придумывай требование. Не исправляй игру.

## 4. Выполни и проверь

- Запусти выбранные тестовые файлы без watch фактической командой проекта.
  Убедись, что обнаружены нужные тесты: «0 tests» не успех.
- Исправляй свои ошибки тестов; не ослабляй ожидания ради зелёного результата.
  Затем запусти весь unit-набор и проверки из `AGENTS.md`: сейчас это проверка
  типов, lint и build; после изменения структуры также fsd-check.
- Не оставляй `.only` или скрывающие дефект `.skip`. Не переписывай посторонние
  тесты/конфиги; отделяй старые падения, дефекты игры и проблемы окружения.

## Отчёт

Коротко: какие файлы и случаи покрыты; точные команды и итог (passed/failed/not run);
что не покрыто и почему, обнаруженные дефекты. Не заявляй полное покрытие по одному тесту.
